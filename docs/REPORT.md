# Звіт про надійність захисту — ЛР №6 «Безпечний клієнт-серверний застосунок з SSL/TLS»

**Виконав:** Кондратюк Тимофій Сергійович, гр. 22340, ФІТУ КУБГ

## 1. Архітектура

```
client.py (SecureClient) ──TLS 1.2/1.3 (ECDHE + AEAD)──► server.py (asyncio)
   │  перевірка сертифіката сервера (CA + SAN)                 │ bcrypt-автентифікація, блокування
   │  [опц.] сертифікат клієнта (mTLS)                         │ токен сесії (TTL) + сесійний HMAC-ключ
   └─ HMAC-SHA256 + seq у кожному запиті/відповіді             └─ JSON-журнал (маскування, ротація)
                                                                        │
                                                          analyze_logs.py → docs/log_analysis.md
```

| Модуль | Призначення |
|---|---|
| `scripts/gencerts.sh` | Локальний CA (ECDSA P-384), сертифікат сервера (SAN: localhost, 127.0.0.1, EKU serverAuth), сертифікат клієнта (mTLS), «чужий» CA для негативних тестів |
| `protocol.py` | Канонічний JSON, HMAC-SHA256, таблиця кодів відповідей |
| `server.py` | TLS-сервер, автентифікація, ролі, контроль цілісності, журналювання |
| `client.py` | Клієнт: вивід параметрів TLS-сесії, логін/пароль, перевірка HMAC відповідей |
| `scripts/add_user.py` | Додавання користувача (лише bcrypt-хеш, пароль через getpass/змінну середовища) |
| `scripts/run_scenarios.py` | 13 сценаріїв (15 з `--mtls`) успішних та атакувальних дій |
| `analyze_logs.py` | Аналіз журналу, виявлення аномалій, Markdown-звіт |
| `tests/test_lr6.py` | 16 автоматичних тестів (pytest) |

## 2. Параметри TLS і ланцюжок довіри

* Мінімальна версія — **TLS 1.2** (`--tls13-only` вмикає лише TLS 1.3); SSLv3, TLS 1.0/1.1 вимкнено.
* Набори шифрів TLS 1.2: `ECDHE+AESGCM:ECDHE+CHACHA20`, без RSA-обміну ключами, SHA1, MD5, NULL → **Perfect Forward Secrecy** + AEAD.
* Фактично узгоджено: **TLSv1.3 / TLS_AES_256_GCM_SHA384**; при обмеженні до TLS 1.2 — `ECDHE-ECDSA-AES256-GCM-SHA384`.
* Ланцюжок: `KUBG LR6 Root CA` (самопідписаний, ECDSA P-384) → `CN=localhost` (сервер). Клієнт довіряє лише `certs/ca.crt`, вмикає `check_hostname` і `CERT_REQUIRED`; **вимкнути перевірку сертифіката в клієнті неможливо** (опції немає навмисно).
* Клієнт виводить: протокол, шифр, суб'єкт/видавця, термін дії, SAN, SHA-256 відбиток сертифіката — це документування встановлення сесії.
* mTLS (`--require-client-cert`): сервер вимагає сертифікат клієнта, підписаний тим самим CA.

## 3. Автентифікація

* Паролі зберігаються лише як **bcrypt** (cost 12) у `users.json` (файл не потрапляє в git).
* Для невідомого користувача виконується перевірка з фіктивним хешем — однаковий час відповіді, без розкриття існування логіна.
* **Блокування:** після 5 невдач у вікні 300 с обліковий запис блокується на 120 с (у демо-сценаріях — 60 с); спроби під час блокування → код 423 і окремий запис у журналі.

## 4. Життєвий цикл токена

1. Після успішного AUTH сервер видає випадковий токен (`secrets.token_urlsafe`) та **окремий сесійний HMAC-ключ**.
2. TTL токена — 300 с; прострочений токен → 401.
3. `logout` анулює токен; повторне використання → 401 (сценарій #7).
4. У журналі записується лише префікс токена (маскування).

## 5. Контроль доступу (ACL)

| Роль | Дозволені команди |
|---|---|
| user | echo, upload, logout |
| admin | усе вище + stats |

Спроба `stats` від ролі user → 403 і подія `acl_denied` (сценарій #3).

## 6. Цілісність повідомлень

* Кожен запит після автентифікації містить `seq` і `hmac = HMAC-SHA256(session_key, canonical_json)`; сервер перевіряє через `hmac.compare_digest`.
* Зміна будь-якого поля → 422 (сценарій #4); повтор номера `seq` → 409 replay (сценарій #5).
* Файли передаються з SHA-256; сервер перераховує хеш перед збереженням.
* Відповіді сервера теж підписані — клієнт перевіряє HMAC кожної відповіді.

## 7. Журналювання і зберігання

* Формат JSON Lines (`logs/server.jsonl`), час у UTC ISO-8601, ID з'єднання, IP, версія TLS, шифр, подія, код.
* Журналюються як успішні, так і **невдалі TLS-рукостискання** (у шаблоні вони губилися).
* Поля `password`, `session_key`, `hmac`, `data_b64` маскуються; токен — лише префікс.
* Ротація: 1 МБ × 5 резервних файлів.

## 11. Ризики та обмеження

| Ризик | Вплив | Захід |
|---|---|---|
| Вимкнення перевірки сертифіката (`CERT_NONE`) у клієнті | MITM, перехоплення пароля | Опція відсутня; `check_hostname=True` жорстко задано |
| Крадіжка/повторне використання токена | Захоплення сесії | TTL 300 с, анулювання при logout, HMAC з сесійним ключем (токен без ключа марний) |
| Компрометація ключа CA | Підробка сертифікатів | Ключ CA зберігати офлайн, не в git; у продуктиві — HSM/корпоративний PKI |
| Відсутність відкликання (CRL/OCSP) | Скомпрометований сертифікат лишається дійсним до кінця терміну | Короткий термін дії, у продуктиві — OCSP stapling |
| Перебір паролів з багатьох IP | Обхід блокування за обліковим записом | Rate-limit на рівні мережі/IP, MFA |
| mTLS вимкнено за замовчуванням | Автентифікація лише паролем | У продуктиві — `--require-client-cert` |
| Журнал на тій самій машині | Зловмисник може стерти сліди | Відправка в SIEM, контроль цілісності журналу |

## 12. Висновки

Створено клієнт-серверний застосунок, у якому канал захищено TLS 1.2/1.3 з ECDHE і AEAD-шифрами, сервер автентифікується сертифікатом від власного CA (опційно — взаємна автентифікація mTLS), користувачі — паролем з bcrypt-хешуванням і блокуванням перебору. Цілісність прикладних повідомлень додатково забезпечується HMAC-SHA256 із сесійним ключем та номерами послідовності проти replay. Усі успішні й невдалі з'єднання журналюються з мітками часу без розкриття секретів, а аналізатор журналу автоматично виявляє 16 типів нетипових ситуацій. Усі 15 сценаріїв атак і відмов відпрацьовано очікувано, 16 автотестів пройдено.
